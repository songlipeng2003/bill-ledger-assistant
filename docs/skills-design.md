# 账单处理：Skills 拆分与落地方案

整理日期：2026-10-23。状态：**设计方案，尚未创建或安装实际 skills**。

## 一、结论：4 个核心技能 + 1 个可选总控

建议按“业务能力与副作用边界”拆分，不按银行或单次任务拆分。

| 技能名称 | 中文名称 | 负责什么 | 不负责什么 | 操作级别 |
|---|---|---|---|---|
| `bank-mail-extract` | 银行邮件交易提取 | 从 Gmail 原邮件、会话和完整账单提取交易及账单摘要，记录来源与覆盖范围 | 不匹配账目、不补账、不删除 | 只读 |
| `bank-ledger-reconcile` | 银行与账本对账 | 获取随手记快照，一对一匹配，给出差异数据、金额及邮件级核对结果 | 不因为发现差异自动修改账目 | 只读 |
| `sui-ledger-entry` | 随手记补录与核验 | 按已授权清单查重并录入消费、退款、利息或还款，保存后重新读取验证 | 不发起真实付款、不擅自改旧账、不删除邮件 | 账本写入 |
| `verified-bank-mail-cleanup` | 已核对银行邮件清理 | 对指定候选会话复核内容与核对证据，在有效确认后移入 Gmail 垃圾箱 | 不清空垃圾箱、不永久删除、不替代完整对账 | 邮件清理 |
| `bank-bill-workflow` | 银行账单处理总流程 | 根据用户任务串联前四种能力，管理范围、状态、确认与最终报告 | 不扩展用户任务或绕过写入/删除确认 | 编排，权限继承实际步骤 |

前四个可以独立使用。只有它们实际可用、并且需要一条自然语言指令串联多个阶段时，再启用总控；不能让一个总控技能依赖尚未安装的技能。

### 为什么不按银行分别建 skill

招商、汇丰、广发主要区别是账单格式、字段含义、账户映射和日期口径，而不是业务动作本身。更适合作为按需读取的资料：

- 招商：每日信用管家、消费卡月账单、分期卡月账单；原交易日、入账日和分期原始日期的区别。
- 汇丰：双语通知、信用卡消费、直接付款授权、转账入账与出账通知；PayMe 的充值/付款链条。
- 广发：按持卡人与卡尾号区分月账单；消费、利息、退款、还款以及存款/溢缴款。

**退款不是一个独立技能，差异报告也不单独拆技能。** 前者是所有环节必须支持的交易类型，后者是对账技能的默认交付。

## 二、基于本次对话，可复用的三个任务场景

### 场景 A：只对账、给差异

示例：“广发银行 2026 年 9 月电子账单和随手记对一下，给我差异数据和金额。”

流程：邮件提取 → 账本快照 → 对账 → 差异报告。**不进入补录或清理。**

本次实例：两位持卡人分别核对；两笔还款可对应；0142 卡消费与利息未见对应支出，9901 卡退款未见对应收入。实际个人数据保留在案件记录中，不写进技能提示词。

### 场景 B：补账，再重新对账

示例：“10 月 10 日之后的招行消费和退款补入随手记，补完再核对。”

流程：明确日期及交易类型 → 重新查重 → 已授权清单补录 → 保存后逐笔重读 → 再对账。

本次实例：补录 21 笔消费后又补录 3 笔退款。以后不能在用户要求完整补账时，因把“消费”理解得太窄而默默遗漏退款；若用户明确只要求消费，则遵守范围，同时说明退款未处理、相关整封邮件仍不能视为完全核对通过。

### 场景 C：核对无误后清理邮件

示例：“汇丰允许前后两天，能对应的日报移入垃圾箱。”

流程：读取有效规则 → 匹配 → 形成邮件级候选清单 → 执行前确认 → 重新检查邮件未变化 → 移入垃圾箱 → 验证结果。

本次实例：汇丰日期容差按用户指定放宽；月账单部分交易匹配，不等于整封月账单可删。所有确认仍按当时工具及平台要求执行，不能写成“第一次授权后永远免确认”。

## 三、每个核心技能的边界与交付

### 1. `bank-mail-extract`

**触发语句**：

- “读取这几封银行邮件的交易。”
- “把招行/汇丰/广发账单整理成明细。”

**关键工作**：

1. 明确邮箱、银行、持卡人/卡尾号、邮件范围和交易范围。
2. 打开原始内容。Gmail 截断时通过页面的“查看邮件全文”补齐，不能仅依赖列表摘要。
3. 区分交易、账单余额/额度、积分、营销内容、转发副本和退信。
4. 提取消费、退款、利息/费用、还款、自有账户转账；保留交易日、入账日、原币、入账币种及金额。
5. 保留一笔真实交易的不同来源观察。双语与转发副本不重复计数，但同日同商户两笔同额交易不能被合成一笔。
6. 记录银行月账单的完整周期，不把“9月账单”直接限定为 9 月 1—30 日。

**交付**：交易观察明细、账单摘要、来源覆盖清单、未能读取的字段。日志中可存会话定位信息，不在通用 skill 中固化个人邮箱、消息链接或卡号。

### 2. `bank-ledger-reconcile`

**触发语句**：

- “帮我对账，列出差异和金额。”
- “补录完了，再对一次。”
- “汇丰允许前后两天重新比对。”

**关键工作**：

1. 确认比较的是交易流水还是余额。没核对期初余额时，不输出确定的余额差。
2. 从随手记获取当前快照。确认日期/账户筛选已生效；分页有加载延迟时，不把上一页或全历史结果当成当前月份。
3. 匹配优先比较持卡人、账户、币种、精确金额、收支方向和可用的商户证据，日期按已确认规则处理。
4. 一对一分配账目。两笔同额独立扣款需要两条账目；同一真实交易的出入通知或重复来源可以共享同一个“交易事件”，但不能因此再次记支出。
5. 信用卡还款应匹配转账入信用卡账户，不能因没有“支出”而判断漏记。
6. 查跨账户、日期差和金额相近的候选时，只输出“疑似”，不把候选自动判定为已匹配。
7. 把交易级结论汇总为邮件级结论。某条已匹配，不代表所在整封邮件或整组会话都已通过。

**差异分类**：

- 未找到对应记录；
- 疑似账户不一致；
- 日期差候选/在规则容差内匹配；
- 疑似金额差异；
- 同额多笔数量不足/疑似重复记账；
- 分类或用途待确认；
- 原币/入账币种信息不足；
- 临时授权或最终入账状态不明；
- 来源未完整读取、会话含其他未处理问题。

**交付**：逐笔匹配、逐笔差异、按卡/币种分开的差异金额汇总、已匹配还款、保留理由、可清理候选。不能把旧账单欠款直接称作“现在还欠的钱”。

### 3. `sui-ledger-entry`

**触发语句**：

- “把漏记的消费补进随手记。”
- “退款也录入。”
- “把已确认的差异逐一补账。”

**前提**：用户已经授权此次录入范围及目标账本；缺失的关键决策需要澄清，不能把只读对账请求变成写入授权。

**关键工作**：

1. 重新查重，使用最新账本，而不是直接执行上轮报告里的“待补录”行。
2. 消费为支出；在本账本既有口径下，退款使用“其他收入 → 退款”，回到原支付账户；利息是费用/利息支出；还款为转账。
3. 原有同日同额但账户不同的记录，不擅自覆盖，也不在疑似重复时再次新增；保留为待确认。
4. 有用途中性分类配置时按配置处理；不能凭银行公司名虚构商品用途。无法确定类别时明确标注，而不是默默套用餐饮。
5. 只有界面强制要求具体时间且来源没有时分时，才使用日期占位时间，并注明“原账单无时分”。日期精度与真实发生时间必须区分。
6. 保存前核对字段，保存后重新读取实际记录，核对金额、账户、方向、日期和笔数。成功提示或输入框清空只是中间证据，最终还要看到保存后的记录。
7. 每次写入都有稳定的核对标识、银行原始商户及来源记录。保存状态不确定时先查是否已写入，**禁止盲目重试新增**。

**交付**：逐笔录入日志、实际账目 ID、已验证数量/金额、未操作原因、更新后的对账结果。

### 4. `verified-bank-mail-cleanup`

**触发语句**：

- “把已经完全匹配的银行邮件移入垃圾箱。”
- “按刚确认的清单删除日报，保留有问题的。”

**关键工作**：

1. 只处理用户要求范围内、具备完整核对证据的邮件/会话。
2. 若一封会话内还含未录退款、其他日期差异、无法确认的交易或用户要求保留的问题，整组保留。
3. 形成固定候选清单：明确邮箱、邮件来源定位、收件日期、交易日期、对应账目和可清理依据。
4. 在实际执行前取得平台所要求的确认；说明机制是“移入垃圾箱”而不是永久删除。
5. 依来源定位打开邮件，复核身份、内容与消息组成未变，不能按不断变化的收件箱行号盲删。
6. 操作后验证垃圾箱标签/恢复入口，逐封记录。垃圾箱中本来就存在的邮件，不算作本次移入。
7. 发现清单外邮件的位置也发生变化时，只记录观察，不推断是谁操作，更不能擅自恢复或处理。

**交付**：已移入、原已在垃圾箱、跳过、失败四类日志；可恢复状态证据；保留邮件及原因。保持每批次清单可追溯。

## 四、项目配置，不写死到技能里的个人规则

以下属于本项目配置，不能推广成所有银行、所有用户的默认行为：

| 配置 | 本次已知口径 | 说明 |
|---|---|---|
| 目标产品 | 随手记 + Gmail | 未来换账本或邮箱，应更换适配器，不修改匹配逻辑 |
| 时区 | Asia/Hong_Kong | 相对日期必须落实为具体日期 |
| 汇丰日期窗口 | 前后 2 个自然日 | 仅在本次已确认条件下使用；不是对招商、广发的全局日期容差 |
| 金额比较 | 同币种，分单位精确比较 | 用整数分或十进制定点，不能用模糊金额容差自动通过 |
| 默认账本 | 当前个人默认账本 | 不把别的账本或家庭成员账户合并成同一账户 |
| 退款分类 | 其他收入 → 退款 | 是本账本现有分类，不代表所有记账系统都使用此口径 |
| 账户映射 | 依据卡尾号、持卡人及实际账本账户 | 缺少尾号的账户映射标记证据与置信度，不只凭同额猜映射 |
| 清理动作 | 经确认移入 Gmail 垃圾箱 | 不包含永久删除或清空垃圾箱 |

“这三天”“上次那封”“这个月账单”等范围不明确时，先列出具体日期和邮件范围；不要未经说明擅自扩大到其他交易日。

## 五、统一的数据结构与执行状态

不建议每个技能自行发明一份金额与状态格式。实际实施时定义简洁合同，但不要把合同做成大而全的业务平台。

### 交易观察与账目

最少保留：

- 来源类型、来源会话/消息引用、来源明细位置、原文证据引用；
- 银行、持卡人/卡尾号的安全标识、账本账户映射；
- 类型：消费、退款、利息/费用、还款、转账、临时授权、非交易；
- 交易日期、入账日期、时间精度；
- 原币及金额、入账币种及金额；金额使用定点字符串或整数最小货币单位；
- 原始商户与规范化商户（后者不能覆盖前者）；
- 来源完整性、真实交易事件与其多个来源观察的关联；
- 实际账目 ID、已匹配证据、状态、待确认原因。

仅凭“日期 + 商户 + 金额”的哈希，不能认定两条来源是同一笔真实交易。

### 每次执行保留三层记录

1. **快照**：当时实际读取到的邮件及账目。
2. **计划**：匹配、待补录、待清理及其依据。
3. **结果**：真正发生且已验证的新增或移入操作。

报告由当前快照与最新操作结果重新生成。历史审计保留，但不要把“退款未录”与“退款已录”等互相冲突的旧状态不断叠加到同一份当前报告，让用户自己判断哪个版本有效。

## 六、建议的实现组织

以下是将来创建时的布局，不是已存在或已安装的技能目录：

```text
账单处理/
├── docs/skills-design.md                  # 本设计稿
├── skills/                               # 评审后创建的技能源码
│   ├── bank-mail-extract/
│   │   ├── SKILL.md
│   │   └── references/                   # 招商/汇丰/广发的解析资料，按需读取
│   ├── bank-ledger-reconcile/
│   │   ├── SKILL.md
│   │   └── scripts/                      # 一对一匹配与金额汇总，纯本地计算
│   ├── sui-ledger-entry/
│   │   ├── SKILL.md
│   │   └── references/                   # 现有分类、查重与保存核验方式
│   ├── verified-bank-mail-cleanup/
│   │   └── SKILL.md
│   └── bank-bill-workflow/                # 需要时再创建
│       └── SKILL.md
├── config/                               # 独立个人配置，不混入通用提示词
└── runs/                                 # 运行快照、计划和结果，含私有数据
```

- 项目内 `skills/` 作为技能源码的组织方式；不声称它会自动被发现。
- 实际使用时可选择项目级可发现目录 `.agents/skills/` 或显式用户级安装位置，按当前 Codex 文档与技能规范部署。
- 通用技能不包含 Gmail 登录信息、真实银行卡号、既有邮件 ID、历史账单或个人文件绝对路径。
- 现有一次性脚本只作为提炼依据，不原样升级成通用技能：其中包含硬编码日期、案例金额、历史状态及个人路径。
- 银行解析、金额匹配、报告生成可以编写纯本地可测试脚本；浏览器操作仍使用环境提供的浏览器能力，不能转而抓取未授权的后台接口。

## 七、验收用例：从这次对话中提炼

| 用例 | 预期行为 |
|---|---|
| 广发9月账单周期跨8月和9月 | 按完整账单周期查账，不仅筛9月 |
| 两个持卡人的同月广发账单 | 按持卡人/卡尾号分别核对及汇总 |
| 消费、利息缺记录，退款也缺记录 | 分别列支出差与退款收入差；不混成同一张卡余额差 |
| 信用卡还款在账本中记为转账 | 正常匹配，不要求再新增一笔支出 |
| 同一天同商户两笔同额消费 | 保留两笔，分配两条不同账目 |
| HSBC 双语正文及转发副本 | 作为来源重复处理，不增加真实交易数 |
| 汇丰日期差1～2天、其他条件一致 | 按已确认的本项目日期规则匹配 |
| 招行同日同额记录在花呗账户 | 标记账户/重复风险，不擅改或盲目再记 |
| 用户要求完整补账，存在退款 | 将退款纳入核对和计划；不因只做支出而声称全部处理完 |
| 月账单包含旧账疑点，新增消费已全部匹配 | 月账单保留，不能因局部完成就清理整封 |
| 日报中消费已录，退款未录 | 日报仍不能完全通过；退款验证后再更新邮件级结论 |
| PayMe 充值通知不含金额 | 信息不足，不独立认定金额已核实 |
| 商户名含 TEMP | 临时授权待确认，不直接当成最终消费 |
| 保存按钮点击后连接中断 | 重新查询实际账目与唯一标识，先确定是否已保存，再决定是否重试 |
| 页面筛选加载中或分页数据重复 | 等待筛选及内容一致，验证页码/记录ID/日期覆盖，不复用错误快照 |
| 邮件新增了回复或交易明细 | 旧清理计划失效，暂停该会话并重新核对 |
| 用户只说“给我差异” | 只读交付；不自动补录或清理 |

### 测试层次

- **本地可重复测试**：使用脱敏/合成数据验证解析、精确金额、一对一分配、覆盖范围、差异汇总、报告状态一致性。
- **技能行为验证**：给真实形态的请求和最少证据，检查是否遵守边界，不仅匹配文案或JSON字段。
- **浏览器只读验证**：读取真实页面状态，检查分页、截断邮件及账户识别，不触发写入。
- **真实写入/清理**：只有获得用户对应授权与必要的执行前确认，才在限定清单上验证。

## 八、落地顺序

1. 先落地 `bank-mail-extract` 与 `bank-ledger-reconcile`：让只读对账稳定、结果可验证。
2. 再落地 `sui-ledger-entry`：先覆盖已有分类、消费/退款/利息/还款及写入防重，不自动改旧账。
3. 再落地 `verified-bank-mail-cleanup`：只接受具备有效证据的固定清单，逐封核验。
4. 前四项成熟后，再决定是否需要 `bank-bill-workflow` 总控入口。
