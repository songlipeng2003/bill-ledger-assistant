# 银行账单处理总流程

本技能只做必要编排，不复制银行解析、页面操作与匹配算法。四个配套技能与本技能一同交付；先确认相应入口存在，缺少时说明能力边界，不假装成功或自动安装外部软件。

## 任务分流

| 用户要求 | 路线 |
|---|---|
| 读取/整理银行邮件 | 仅 `bank-mail-extract` |
| 对账/列差异 | `bank-mail-extract` → `bank-ledger-reconcile`，只读结束 |
| 补录并复核 | 提取 → 对账 → 在授权清单上 `sui-ledger-entry` → 重新对账 |
| 核对无误后清理 | 提取 → 对账 → `verified-bank-mail-cleanup`；保留不完整会话 |
| 补账后清理 | 提取 → 对账 → 已授权补录 → 重读核验 → 重新对账 → 清理执行前确认 |

从同级目录按实际任务加载相应 `SKILL.md`；不因能读取全部技能就一次加载所有参考资料。不启用子代理，除非用户或适用指令明确授权。

## 已核验补录后的默认清理

读取[本项目配置](references/project-policy.md)的 `post_entry_cleanup`。启用后，已授权补录实际保存、回读核验并重新对账成功时，自动调用 `verified-bank-mail-cleanup` 准备对应邮件的固定清单，不再另问“是否要进入清理步骤”。本轮明确要求保留邮件或只记账时，以本轮要求为准。

- 单纯读取/对账、保存失败或不确定、尚未完整核对的会话不触发；一笔已记不能扩大为清理整封未核对月账单，也不扩展到其他邮件。
- 只移入垃圾箱；逐封重读、范围、指纹、消息/附件库存及匹配要求不变。
- 实际执行遵循当前工具的确认要求；浏览器要求删除前确认时，对固定整批清单确认一次。已有针对该清单、在执行前取得的明确确认且风险未变时不重复询问，但长期“以后不再确认”的偏好不能替代工具强制的执行前确认。
- 这是本项目任务内的默认后续步骤，不创建后台邮箱监控或定时任务。

## 必要上下文

- 将“这三天/这几笔”落实到绝对日期和来源，三笔退款不自动等于三个交易日。删除前不能用未经确认的推断扩展范围。
- 新一轮按最新账目与邮件快照重算，不照搬历史报告的未录/可删状态。
- 读取[本项目配置](references/project-policy.md)时确认该文件指向的本地配置适用于当前任务。个人账户映射不是通用银行规则。
- 工具断连、UI变动、保存不确定都按对应技能的恢复方式处理，不为继续执行而换成隐藏接口。

## 执行记录与最终交付

每次保留快照、计划、结果三层；报告从本轮有效结果生成，历史日志另外留档，不追加互相矛盾的“尚未录/已录”状态。

只读结束就交付差异；已授权操作结束则说明实际完成、未完成、跳过原因和是否改账/移邮件。始终区分“准备好”“用户已确认”“执行中”“已验证”。不自动安排后续运行、移动历史金融文件或进行银行支付。
